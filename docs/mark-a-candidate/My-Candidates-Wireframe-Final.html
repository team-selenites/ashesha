Annotations

  1. Tab order inside every card: Open, then the expand chevron. Visible focus is a 3px Space Angel ring with white offset (shown on the first Open button).
  2. One visible label, “Open”, on every compact and expanded card. Each Open button has its own accessible name built from its record, for example Open observation SAMPLE-0012 for target Sample Comet A, image 12. All five names are listed on screen 12. The card itself is not a click target.
  3. Compact cards carry two actions only: Open and expand/collapse. Edit note, Copy Observation Link, Copy Candidate Summary and Delete live in the expanded card, so Delete is never one click away.
  4. Groups are ordered by the newest saved candidate; cards inside a group newest saved first. Switching view or sort never changes records. All view and sort combinations are specified on screen 6.
  5. Toolbar order is Search, Status, Sort by, View. They share one row and wrap in that order without overlap. On mobile they move into the disclosure panel (screens 14 and 15).
  6. New in this revision: Export text and Export JSON sit in the header, secondary style. The earlier wireframe did not show where they live; this placement is proposed and needs Pawana’s review. Export rules are on screen 11.
  7. Thumbnail: shown when available; otherwise a neutral placeholder with the same 72px footprint (SAMPLE-0003 has no thumbnail). Never an unrelated image. Status is symbol plus text. Null values read “Not available”. The result count is a polite live region.

Annotations

  1. Chevron: aria-expanded and aria-controls point at the details region; the name includes target and image number. Several cards can be open at once. The compact card stays separate from the expansion.
  2. Actions in the expansion: Open (primary), Edit note, Copy Observation Link, Copy Candidate Summary, Delete. The visible label “Open” matches the compact card, but the accessible name ends “, from card details” so the two Open buttons on one card are never identical. Other actions carry the record in their names, e.g. Delete candidate SAMPLE-0012, Sample Comet A, image 12.
  3. Viewer description is note: optional, read-only, never overwritten. If missing or null it reads “No description available” (SAMPLE-0003). Personal note is personal_note: optional, editable. If missing or empty a neutral prompt invites the user to add one (SAMPLE-0007).
  4. The two notes are never merged. note is not part of the 12-field viewer event contract. Its source and transfer mechanism are to be confirmed by the viewer team; the saved record accommodates it and the interface keeps it.
  5. Status is shown exactly as the viewer supplied it. It cannot be edited here (screen 12). The metadata grid shows scientific fields only; image_url and view_link stay in the record and are reached through Open or Copy Observation Link.
  6. Image number “12 of 40”, Obs ID, observation date, saved time and RA/Dec are separate fields. The observation date and the saved time are never interchanged.

Annotations

  1. Replaces the earlier timed snackbar. No timer, no snackbar and no confirmation modal. Delete swaps the card for an inline row in the same position: “Candidate deleted.” and Undo.
  2. Focus moves to the inline row (it receives programmatic focus, tabindex="-1"), so Undo is the next tab stop. The outcome is announced: “Candidate deleted. Undo is available until you leave My Candidates.” The row carries text and a button, not colour alone.
  3. The row stays until the user leaves the My Candidates view. Leaving commits the deletion and Undo is no longer offered. Nothing times out. Switching view, sort or filters does not leave the view; a pending row stays visible (recommended, to be confirmed in implementation).
  4. Undo restores the exact original record: same candidateId (no new ID), all viewer observation fields, image_number, image_count, note when available, personal_note, the original savedAt, and the original group and list position. Scientific metadata is never modified.
  5. After Undo, focus moves to the restored card’s expand button (never to Open, so a stray Enter does not navigate away) and “Candidate restored.” is announced.
  6. Edge cases for implementation to confirm: several pending rows can coexist, each with its own Undo; if the last candidate is deleted the empty state appears only after the view is left; a viewer save of the same obs_id while a deletion is pending is treated as a duplicate of the pending record (screen 9) and offers Undo; recommended persistence is to remove the record from localStorage at Delete, hold it in memory for Undo, and write it back on Undo; if that write fails, show the save-failure message and keep the row.
  7. Dependency: “leaving the view” needs a concrete definition in the integrated page, because #mc-root sits below the viewer. Proposed: page navigation or unload, a route change, or unmounting #mc-root. Confirm with the viewer team.

Annotations

  1. Rule. Duplicate check key = a non-empty obs_id, on its own. If it matches an existing candidate, the module does not create another candidate, does not silently overwrite, and does not touch the existing personal_note. (The review asked for “update or flag”; this design flags, because updating could overwrite the user’s note or scientific data.)
  2. The message “This observation is already in My Candidates.” is announced. View existing candidate scrolls to the existing card, expands nothing, moves focus to its expand button and keeps the card marked Already saved (check mark and text) until the next list change.

  5. obs_id is the only identifier for an image. image_number is never part of the key: it is the position in the target’s sequence and can change when the data set is rebuilt.

Annotations

  1. Failures use the label “Error:” in text plus a heavy left rule, with role="alert", never colour alone and no new palette colour. No raw technical error is shown to ordinary users; details go to the developer console.
  2. Never announce success when an operation fails. A failed save does not claim a candidate was saved and does not alter the list; the retry re-uses the same viewer payload. A failed copy leaves the record untouched and focus stays on the button that was pressed, which is the retry path.
  3. Load failure is not an empty list. While the load has failed the module does not write to localStorage, so an unreadable store can never be overwritten by an empty one. If localStorage is unavailable altogether (blocked, private mode), the same load-failure state is shown and saving reports the save-failure message.
  4. Success messages stay: “Observation link copied.” and “Candidate summary copied.” Full message catalogue, including proposed wording for Open, Export and no-observation cases, is on screen 12.

Annotations

  1. Summary rules. One field per line, in the order above. Units are kept (µm, degrees). Unavailable values read “Not available”; nothing is invented. “Viewer description” falls back to “No description available” and “Personal note” to “No personal note”. Image is “[image_number] of [image_count]”. Status is the human-readable label.
  2. Observation date and saved time are separate lines. “Observation date” is the astronomical date (date); “Saved” is the ISO 8601 savedAt in UTC, unambiguous when pasted into email or a research note. Plain text uses an ASCII minus (-12.345°) so values paste cleanly into other tools; the screen uses a typographic minus.
  3. Observation link is the saved view_link converted to an absolute URL at runtime from the browser’s current location (new URL(view_link, location.href)). No domain is hard-coded. The link never includes the notes.
  4. The closing line “A saved candidate is not a confirmed discovery.” is part of every summary. The summary is text only, with no thumbnail.
  5. Long-list rule (Export Text). Includes every saved candidate, in the visible order of the current view and sort, with a clear divider between records. It is never silently truncated and no candidate is silently omitted. No character limit is invented. If the browser cannot complete the operation, a clear failure message is shown (proposed: “Could not export the candidates. Please try again.”) and no partial file is offered. Search and status filters do not shorten the export; to be confirmed.
  6. Export JSON writes the wrapper format, version, exportedAt, candidates (see sample-candidates.json). There is no import: exported files are not read back into the app.

Storage

Candidates persist in browser localStorage under selenites.myCandidates.v1. It is browser-specific and device-specific, not synced, not encrypted, and can be erased when browser data is cleared. JSON export is a backup copy to keep; there is no import, so it does not restore data into the app.
